## Findings

### 1. [MAJOR] In-match controls legend exists but is permanently hidden (display:none, never toggled)
- Where: index.html:1191
- Why: #controls-hint (markup at index.html:1910-1917 — the only in-match key legend covering sails, anchor, helm, ammo keys) is killed by CSS `#controls-hint { display: none; }` at 1191-1193, and `rg controls-hint src -g '*.ts'` returns zero hits — no code ever shows it. The only reachable key list is buried in the Settings menu panel (index.html:1676-1683), unreachable mid-match without losing pointer lock and leaving the HUD. This is why sail raise/angle controls are undiscoverable: their hints only appear AFTER you already found and entered the sail ring (Game.ts:7821).
- Fix: Bind a hold-to-show key (e.g. H or F1) following the existing KeyM pattern in Game.ts bindMapUiActions (2295-2305): toggle a .visible class on #controls-hint, and add `#controls-hint.visible { display:block }`. Regenerate its text from one KEYBINDS table also used by the settings block so the two never drift; show it automatically for the first ~45s of a player's first match.

### 2. [MAJOR] Cannon ammo key hint says [4/5/6] but the actual keys are 5/6/7
- Where: src/client/core/Game.ts:7807
- Why: InputManager.ts:72-74 binds Digit5→cannonball, Digit6→firebomb, Digit7→chainshot (matching settings text '5/6/7 · Cannon Ammo', index.html:1680). But the at-cannon context label says '[4/5/6] shot type' (Game.ts:7807) and the cannon interaction label says 'Broadside cannon N · [4/5/6] ammo' (Game.ts:10103). Pressing 4 as instructed switches your hand weapon slot to cutlass (InputManager.ts:71, server Match.ts:960) instead of changing shot type — the hint actively misleads during combat.
- Fix: Change both strings to '[5/6/7]' at Game.ts:7807 and Game.ts:10103, or better, derive the hint from a single CANNON_AMMO_KEYS constant shared with InputManager so future rebinds can't desync.

### 3. [MAJOR] No FOV-compensated mouse sensitivity while scoped — sniper (and any spyglass) turns 5x too fast
- Where: src/client/input/InputManager.ts:239
- Why: applyLookDelta (InputManager.ts:239-244) applies a fixed 0.002*sensitivity rad/px regardless of camera FOV. When eye_of_reach ADS drops FOV from 74° to 14° (Game.ts:7364-7370, constants/index.ts:268) angular sensitivity per screen-pixel becomes ~5.3x, making precise long shots twitchy. setSensitivity is only called from the settings slider (MenuController.ts:381,490) — nothing scales per-aim. A spyglass zooming beyond 14° (e.g. 6°) would be unusable without this.
- Fix: Add `private fovScale = 1` + `setLookFovScale(s: number)` to InputManager and multiply k by it in applyLookDelta (239-244). Drive it from Game.updateCamera where scopedFov is resolved (Game.ts:7364-7370): `this.input.setLookFovScale(scopedFov ? Math.tan(degToRad(scopedFov/2)) / Math.tan(degToRad(74/2)) : 1)`.

### 4. [MAJOR] Sail trim hint 'Trim Right [F]' shown in contexts where Q/F do nothing; helm label omits its W/S trim ability
- Where: src/client/core/Game.ts:7667
- Why: Q/F/C/Z only function while player.atSails (server gate at Match.ts:1156-1163). Yet the ship-status panel renders 'Trim Right [F]' / 'Trim Left [Q]' (Game.ts:7664-7668) whenever you're on a ship — at the helm, on deck, at a cannon — where pressing F does nothing, teaching players the keys are broken. Meanwhile the at-helm context label (7813: 'A/D steer · compass on starboard side') omits that W/S trims sails at the helm (Match.ts:1227-1228), which IS available. Sail control hints are split across 5 keys, 2 stations and 4 different strings (7667, 7813, 7821, 10032) with no single consistent explanation.
- Fix: In updateHud, gate the key-name trim hint on the player actually being at a station where it works: `const trimHint = player.atSails ? 'Trim Right [F]'... : 'Trim at sail ring'` (7664-7668); and extend the helm label at 7813 to 'A/D steer · W/S trim sails · compass on starboard side'.

### 5. [MAJOR] Debug overlay 'draw 1 | tris 1': renderer.info read after post-fx composer auto-resets it per pass
- Where: src/client/core/Game.ts:6106
- Why: updateDebugPerfPanel reads this.renderer.renderer.info (Game.ts:6058, printed at 6106) after Renderer.render() → postFx.render() → composer.render() (Renderer.ts:503-504, PostFx.ts:106-107). WebGLRenderer.info.autoReset defaults to true, so counters reset on every internal renderer.render call inside EffectComposer; by the time Game reads them they reflect only the final full-screen output-pass quad: 1 draw call, ~2 triangles. The panel's scene stats are useless for perf triage.
- Fix: In Renderer's constructor set `this.renderer.info.autoReset = false`, and call `this.renderer.info.reset()` at the top of Renderer.render() (Renderer.ts:494) before the sky/composer work — end-of-frame reads in updateDebugPerfPanel then accumulate all passes for the frame.

### 6. [MINOR] Powder keg key [G] is undocumented anywhere in the live HUD
- Where: src/client/core/Game.ts:9184
- Why: Keg flow is hold-G to preview, release G (or LMB while holding) to place (InputManager.ts:63-67, 82-87, 98-104). The HUD keg panel says only 'Powder Kegs (equipment) / 2 ready' (index.html:1858-1861, value from getKegSummary Game.ts:9184-9191) and the ambient context label appends the same summary without a key (7844). 'G · Keg' exists only in the settings menu (index.html:1681) and the permanently-hidden #controls-hint doesn't mention G at all (1910-1917).
- Fix: Append the key to the summary: in getKegSummary (9184-9191) return '... ready · hold [G] to place' when kegs>0, and change the #keg-status label at index.html:1858 to 'Powder Kegs [G]'.

### 7. [MINOR] Crow's nest prompt breaks the '[X] Verb' convention used by all 20+ other prompts
- Where: src/client/core/Game.ts:10047
- Why: Every interaction prompt is formatted '[X] ...' or '[Hold X] ...' (9858, 9874, 9889, 10019, 10031, 10063, 10102, etc.) except the crow's nest candidate: 'Press X to Climb Crow\'s Nest' (10047). Inconsistent copy weakens the visual pattern players scan for, and it's the longest string in the prompt slot.
- Fix: Change Game.ts:10047 to '[X] Climb Crow\'s Nest' to match the convention (leave-state variant at 7824 already reads '[X] Climb Down From Crow\'s Nest').

### 8. [MINOR] Vestigial sail_hoist/sail_angle intents and SailControlMode that is never set
- Where: src/shared/types/index.ts:637
- Why: InteractIntent includes 'sail_hoist' and 'sail_angle' (types/index.ts:637-638) and Player carries sailControlMode: 'hoist'|'angle'|null (119, 149), but the client only ever emits 'sails' (Game.ts:10025-10034), the server maps all three to the identical enterSails (Match.ts:3098-3107), and sailControlMode is only ever assigned null (Match.ts:333, 667, 708, 1039; BotSystem.ts:527). Dead scaffolding from a split-station design misleads implementers into thinking two sail modes exist.
- Fix: Either delete 'sail_hoist'/'sail_angle' from InteractIntent, the duplicate switch cases at Match.ts:3098-3107, and the SailControlMode field — or actually implement the split (prompt cycling hoist vs angle) if that UX is still planned. Removal is safe: no other references exist.

### 9. [MINOR] PlayerInput.barrelTakeAll is dead on the real client — always false
- Where: src/client/input/InputManager.ts:167
- Why: buildInput hardcodes `barrelTakeAll: false` (InputManager.ts:167) and nothing in Game.ts ever sets it; the actual take-all path is a second [X] press with intent 'barrel' (prompt flips to '[X] Take All' at Game.ts:9874; server tryOpenBarrel returns takeAllFromBarrel on the second open, IslandSystem.ts:16-27). The server still maintains a full one-shot path for the field (Match.ts:1028-1033), suggesting a shortcut key that was never wired — misleading surface for anyone extending barrel UX.
- Fix: Either wire a real shortcut (e.g. hold X or a dedicated key sets barrelTakeAll while barrelBrowse is open) or remove the field from PlayerInput (types/index.ts:677) and the server branch at Match.ts:1028-1033, keeping the double-[X] flow as the single mechanism.

### 10. [MINOR] Eye-of-Reach viewmodel counter-scale hardcodes HIP_FOV=74, mismatching non-74 base FOVs
- Where: src/client/core/Game.ts:9807
- Why: The ADS counter-scale divides tan(scopeFov/2) by tan(74°/2) with HIP_FOV hardcoded (Game.ts:9807, 9827-9833), but updateCamera's actual base FOV is 78 while swimming and 64 while aiming a firearm un-scoped (7370), plus a speed-based FOV kick up to +4° (7468-7472). Scoping while swimming or at sail-speed leaves the scope tube slightly wrong-sized/popping. Any spyglass copying this pattern inherits the bug at a stronger zoom where the error is far more visible.
- Fix: Replace the constant with the camera's current pre-kick target: pass targetFov (or read this.renderer.camera.fov) into syncLocalViewWeapon and use it as hipHalf's source at 9828 instead of HIP_FOV=74.

### 11. [MINOR] All 'climb' interactions are instant teleports; no ladder traversal state exists for crow's nest or cliff shores
- Where: src/server/core/Match.ts:713
- Why: enterCrowNest snaps the player straight to the nest (Match.ts:713-719 → snapPlayerToCrowNest 4299-area), ship boarding teleports to deck (tryBoardFromLadder 2983-2995), dock ladders teleport too — there is no climbing state, animation, or interruption window anywhere. Meanwhile cliff shores are hard movement-blocked by resolveSlopeBlock (PhysicsSystem.ts:1355-1376, LOCO.SLOPE_MAX revert), so steep island edges are dead ends with zero affordance or prompt explaining why the player is stuck. For the planned cliff-shore + crow's-nest experience this reads as pop-teleports and invisible walls.
- Fix: Introduce a shared 'climbing' player sub-state: server lerps position along a ladder segment over N seconds (new field like player.climbProgress driven in applyInput, reusing the atCrowNest occupancy check at Match.ts:674-694), client plays a hand-over-hand viewmodel via the existing syncLocalViewPocket pattern (Game.ts:9489). For cliffs, surface a context label ('Too steep — find a beach or ladder') when resolveSlopeBlock reverts repeatedly, using the existing contextLabel plumbing at Game.ts:7845-7846.

### 12. [MINOR] Interact prompt reacts up to ~120ms late because the HUD updates at 8-12Hz while intent scanning runs at 30Hz
- Where: src/client/core/Game.ts:6319
- Why: refreshInteractIntentForNet recomputes the interact winner at 30Hz (6326-6330) so the network intent is fresh, but the visible prompt text only updates inside updateHud on hudTimer = 0.08s (0.12s at low effectScale, 6316-6320). Swinging the camera across a chest/cannon shows the prompt lagging the crosshair by 2-4 frames — the game feels less responsive than it is, and on the click-to-interact fallback (bindInteractPromptClick 10674) users can click a prompt that no longer matches lastInteractKind.
- Fix: Split prompt refresh out of updateHud: after refreshInteractIntentForNet at 6328, when lastInteractKind changed, immediately update ui.interactPrompt/contextLabel from the already-computed getLookInteraction result (reuse the candidate object instead of re-running it in updateHud at 7790-7792), keeping the heavier panels on hudTimer.
