## Findings

### 1. [MAJOR] Players do not stick to the rendered deck: renderer applies heave/pitch/roll to hulls but all standing surfaces are flat planes
- Where: src/server/systems/PhysicsSystem.ts:564
- Why: Client pins the hull mesh to the exact wave surface (mesh Y = ship.position.y + ship.heave, ShipRenderer.ts:2582-2586) and tilts it by server pitch/roll (ShipRenderer.ts:2651-2652, clamps ±0.5/±0.6), but players stand on deckY = ship.position.y + stats.height + 0.1 (PhysicsSystem.ts:564, getShipFloorY :1861-1879) and the client renders them at raw server Y with yaw-only XZ re-projection (Game.ts:6385-6404). Net: feet float/clip vs the visible deck by the heave residual (±0.1-0.3m typical, ±2 clamp) plus tilt offset local.x*sin(roll)−local.z*sin(pitch) (~0.5m at a galleon rail in a heeled turn, roll up to 0.11 from windHeel+turnHeel), ~1m sway at the crow's nest (pinned flat at :606-611 while the masthead 8-11m up swings with roll). First-person deck visibly bobs through the camera since updateCamera eye pos (Game.ts:7440) also ignores attitude. The renderer's own comment (ShipRenderer.ts:2994-2995) assumed attitudes 'stay small' — true only for the client fallback (±0.05/±0.06), not the server fields that are now always sent.
- Fix: Server: add the attitude term already used for flood holes (evaluateSectionFlood PhysicsSystem.ts:167) to getShipFloorY (:1861), the deck/hold/stair returns, the crow's-nest pin (:607, plus lateral nestY*sin(roll/pitch) displacement), and Match station snaps (Match.ts:4267-4297): floor = base + ship.heave + local.x*sin(ship.roll??0) − local.z*sin(ship.pitch??0). Client: in getPlayerRenderPosition's on-ship branch (Game.ts:6385-6404) apply the identical Y correction from the same snapshot fields, or transform the player's ship-local offset through shipRenderer.getShipGroup(ship.id).matrixWorld so players/camera ride the exact rendered deck.

### 2. [MAJOR] Trimmed square sails rotate away from their static merged yardarms
- Where: src/client/rendering/ShipRenderer.ts:2681
- Why: update() rotates each square sail about the mast axis toward ship.sailAngle (sail.rotation.y += angleWrap(targetSailYaw−...) at :2681; MAX_SAIL_ANGLE = PI*0.48 ≈ 86°, constants/index.ts:95), but the yard the sail hangs from (:1774-1782) is a plain cylinder baked into the static merged hull mesh (mergeStaticMeshes :2392 — yards are not in the exclusion set :2378-2391). At any non-zero trim the canvas's top edge swings away from the spar; at proper beam-reach trim (~±80°) the sail hangs in mid-air nearly perpendicular to its own yard — a glaring arcade artifact on every actively sailed ship.
- Fix: Per mast, create a trimPivot Group at (0, H+mastH*0.82, mastZ) containing the yard, the sail (repositioned relative to pivot), and optionally the furled roll; add trimPivot to the merge exclusion set; in update() rotate trimPivot.rotation.y toward ship.sailAngle instead of the sail mesh, keeping the cloth-flutter code (updateSailCloth :3042) on the child sail. Also consider clamping the visual trim to ~±0.6 rad (real brace angle) while keeping the gameplay value.

### 3. [MAJOR] Ship rocking freezes/steps at observed 1000-1400ms snapshot ages because stale server attitude is preferred over the deterministic client Gerstner
- Where: src/client/rendering/ShipRenderer.ts:2571
- Why: update() prefers server pitch/roll/heave whenever the snapshot carries them (:2571-2577) — and PhysicsSystem always writes them (:397, :1463-1464) — so the smooth client fallback computeWaveMotion (:2996-3009) is dead code in practice. With the debug overlay showing snapshots 1000-1400ms apart, hull attitude is sampled at <1Hz: ships hold a frozen tilt then spring to the new one each snapshot (attitude lerp 1−exp(−3.4..3.8dt) converges in ~1s, i.e. continuously chasing stale data). Position has the same problem: extrapolation is hard-capped at 0.14s (:2567) so a 12 m/s ship freezes then jumps ~12m per snapshot despite the fast position lerp (:2588-2592). This is a large part of why ships read as static/lifeless.
- Fix: The Gerstner field and ocean clock are shared and deterministic (gerstnerHeight/getOceanRoughness utils:252-282; clock synced Game.ts:2738-2742, :5967-5968), so compute wave attitude client-side every frame from computeWaveMotion (raise its clamps to match the server's ±0.45/±0.55) and treat the server pitch/roll only as a slow correction for the non-deterministic parts (windHeel/turnHeel), e.g. blend serverValue−clientWaveValue as an offset. Likewise compute heave target as gerstnerHeight at the interpolated position rather than ship.position.y+ship.heave when snapshotAge > ~0.25s, and scale the extrapolation cap with observed snapshot cadence (or interpolate between the last two snapshots).

### 4. [MAJOR] Slab-sided hull: one near-vertical topside facet per side, plus straight box wales/strakes that ignore the hull taper
- Where: src/client/rendering/ShipRenderer.ts:165
- Why: makeHullGeometry (:165-223) lofts only 6 stations with 3 vertical slots (deck/chine/keel, :167-172): the entire topside is a single quad strip ~7-10° off vertical amidships (deck half 0.56W vs chine 0.50W over 0.75H) with no flare or tumblehome, and indexed smooth normals (:221) erase even the chine crease — exactly the 'flat vertical slab' in the screenshots. The would-be 'curved strakes' are straight BoxGeometry runs at constant offset: planking strips at x=±W*0.485 spanning L*0.7 (:1102-1112) and wales at ±(W*0.5+0.01) spanning L*0.8 (:1117-1125), while the actual half-width tapers to 0.26W/0.055W near the ends — so the rails float visibly off the hull near bow and stern and reinforce a rectangular silhouette.
- Fix: Extend each station in makeHullGeometry to 5 vertical slots (sheer/upper-topside/lower-topside/chine/keel) with outward flare (upper half-width ~1.08x of lower) and mild tumblehome aft, and add 2-4 intermediate stations (8-10 total); keep the existing quad/cap generation pattern (:189-215). Replace the straight strip/wale boxes with segmented runs that sample the station half-widths per z (reuse the stations array — e.g. a helper waleHalfWidth(z) interpolating :167-172) so rails hug the planking; this also fixes the team stripe visually since it already follows the hull surface via UVs.

### 5. [MAJOR] Arcade team stripe: neon palette painted at 0.9 alpha with emissive accents and an emissive box-stripe proxy
- Where: src/client/rendering/ShipRenderer.ts:896
- Why: TEAM_COLORS (src/server/core/Match.ts:46-51) are pure neons (0x44FF88, 0x44FF44, 0x88FF44 = the greens in the screenshots). getTeamHullTexture (:896-916) paints that raw color at globalAlpha 0.9 with zero weathering over the wood; teamAccentMat (:1024-1030) adds emissive (0.22) team color to the transom band (:1129-1134) and figurehead accents; and the distance proxy renders emissive-0.3 stripe boxes (:946-949) on a literal BoxGeometry hull (:940) visible beyond 170-285m (:2559). Emissive saturated green on brown wood reads as a plastic toy, matching 'arcade-looking green stripe'.
- Fix: In getTeamHullTexture, blend the team color ~55% toward a painted-wood base (e.g. lerp RGB toward #3a2a18), drop alpha to ~0.7, and overlay the existing woodCanvas separator/grain strokes on top of the band for wear; remove emissive from teamAccentMat and the proxy stripeMat (keep saturated/emissive color only on the flag :2295-2301, pennant :1750, and sail band sailTexture :108-116, which carry team-read at distance); optionally derive a desaturated 'paint' variant of TEAM_COLORS in shared constants so server-side palette stays for UI.

### 6. [MINOR] Proxy LOD pops: box hull, different mast heights, and toy proportions vs the detail model
- Where: src/client/rendering/ShipRenderer.ts:918
- Why: buildShipProxy (:918-990) uses BoxGeometry hull/deck and mast height H*(3.25/2.85) (:960) while the detail model uses H*(3.6/3.1) (:1731), so crossing detailDistance (170m on 'low', :2559) visibly pops silhouette and rig height. The proxy's flat vertical sail planes never billow and its slab hull is a big contributor to distant ships reading as slabs.
- Fix: Reuse makeHullGeometry(W,H,L) for the proxy hull (it merges to one mesh; vertex cost is trivial) and match mast heights to the detail constants; keep the single-texture sail planes but tilt them slightly (rotation.x ~0.06) and scale.y with sailHeight as already done at :2598.

### 7. [MINOR] Client/server desired-trim constant mismatch (0.95 vs 0.92) desyncs luff/billow visuals from actual sail power
- Where: src/client/rendering/ShipRenderer.ts:2668
- Why: The renderer computes desiredTrim = sin(rel)*MAX_SAIL_ANGLE*0.95 (:2668) to derive trimCatch for flutter/billow, while the server uses *0.92 (PhysicsSystem.ts:320) for the authoritative trimEfficiency. A perfectly trimmed ship (server trimError=0) shows slight residual flutter/depower visuals, and the two drift further near the trim limits.
- Fix: Export a shared helper (e.g. computeDesiredTrim(signedRelative) in src/shared/utils/index.ts next to sampleWind) returning sin(rel)*SHIP.MAX_SAIL_ANGLE*0.92 and use it in both PhysicsSystem.ts:320 and ShipRenderer.ts:2668.

### 8. [MINOR] Per-frame computeVertexNormals on every visible sail's cloth sim
- Where: src/client/rendering/ShipRenderer.ts:3079
- Why: updateSailCloth recomputes vertex normals for each 11x8-vert sail every frame (:3079) for every detail-near ship (up to 4 sails/ship incl. jib) — needless CPU in the hot loop; normal deltas on a low-amplitude ripple are visually negligible for a DoubleSide rough cloth. The holdWater ripple (:2787-2791) similarly runs per-vertex every frame when flooded.
- Fix: Skip computeVertexNormals entirely (keep rest-pose normals from :279-280) or recompute every 3rd frame keyed off a frame counter; if lighting response is missed, approximate by rotating the material's normal via sail.rotation.x flutter already applied at :2682.

### 9. [MINOR] Player feet sink ~6cm into the deck planks
- Where: src/client/rendering/ShipRenderer.ts:1301
- Why: Deck slabs are centered at deckTopY = H+0.084 with 0.15 thickness (:1301-1311) → top face at H+0.159, but the server stands players at H+0.1 (PhysicsSystem.ts:564) and player meshes are feet-origin (makePlayerMesh, Game.ts:251-290, torso center y=1.28). Every pirate stands ankle-deep in the deck; same 0.06m burial for barrels/props aligned to H+0.1 stations.
- Fix: Set deckTopY = H + 0.025 so the slab's top face lands exactly at the server's H+0.1 standing plane (or bump the shared stand offset to stats.height+0.16 in PhysicsSystem.ts:564/:1863/:1251 and Match snap points — but changing the renderer is safer since the server constant is referenced in many places).
